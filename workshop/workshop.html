Context: What is Curation?

Research Data Curation

The ongoing process of managing research data so that it is FAIR:

  • Findable

  • Accessible

  • Interoperable

  • Reusable

Curation vs. Preservation

We organize, describe and clean files. Long-term preservation is handled by Digital Preservation services.

Generalist Repositories (FRDR)

The Federated Research Data Repository (FRDR) is a bilingual platform for sharing Canadian research data:

  • Well-documented, stand-alone data.

  • Medium-to-large datasets via Globus.

  • Storage mirrored across national host sites.

Let’s start with a shared definition. Research data curation is the ongoing work of managing data so that it is FAIR: findable, accessible, interoperable and reusable. I want to flag one distinction up front: curation is not preservation. We organize, describe and clean files, while long-term preservation is handled by our Digital Preservation colleagues. Growing Dataset Scale

Datasets keep growing in file count and storage size.

  • File Counts: a few files up to 100K+.

  • Storage Size: under 1 GB up to 1000+ GB.

  • Format Diversity: hundreds of extensions (csv, pdf, jpg, xlsx).

Why do we talk about large datasets in particular? Because datasets keep growing, in two ways. In file count, from a handful of files up to more than a hundred thousand in a single deposit. And in size, from under a gigabyte to over a terabyte. On top of that, we see hundreds of different file extensions. The two charts show how both trends have climbed over time. This is the reality we design our workflows around.

The Data Curation Workflow

We utilize the Data Curation Network’s CURATED steps to ensure datasets meet high standards:

  • Check files and metadata.

  • Understand and run files.

  • Request missing information.

  • Augment metadata.

  • Transform file formats.

  • Evaluate FAIRness.

  • Document curation process throughout.

FRDR interactive curation pipeline. Working with the researcher is an essential element of this project

To give our work some structure, we follow the CURATED steps from the Data Curation Network: Check files and metadata, Understand and run the files, Request missing information, Augment metadata, Transform formats, Evaluate FAIRness, and Document everything along the way. The toolbox you will see today lives mostly in the first two steps, Check and Understand, because that is where automation saves us the most time. And notice the caption under the diagram: working with the researcher is essential. Tools support that conversation, they never replace it.

Curation Challenges and Bottlenecks

  1. Dataset Heterogeneity: Number of files and format variety.

  2. Many Files: processing tens of thousands of files quickly and consistently.

  3. Large Files: gigabyte-scale files need serious computing power and memory.

  4. Varying Documentation: Missing READMEs, orphaned variables, and obscure custom scripts.

  5. Reproducibility and Security: hardcoded paths and PII (emails, keys), checked at scale.

So what makes this hard? Five things. First, heterogeneity: many formats and many layouts. Second, many files: how do you process tens of thousands of them quickly and consistently? Third, large files, which need serious computing power and memory. Fourth, documentation varies a lot, with missing READMEs and orphaned variables. And fifth, reproducibility and security: hardcoded paths, or personal information like emails and keys hiding inside files. Each demonstration that follows maps back to one or more of these challenges.

Module 1: High-Level Profiling

First-stage triage of an incoming dataset.

  • Why: Manual directory inspection is limited at scale.
  • Obtained:
    • Inventory of extensions and sizes.
    • Deep metadata (author, dates, MIME type).
    • Risk flags (empty, junk, executables).
  • Problems Solved:
    • Extension mismatch: hidden or falsified formats.
    • Security risks: executables and junk.
    • Triage: volume and complexity.
    • Scale: ExifTool runs up to 2,000 files; the inventory always completes.
  • Tools: tidyverse, ExifTool, exiftoolr.

Module one: high-level profiling. Whenever a dataset arrives, this is the very first thing we run. Inspecting a directory by hand does not scale, so the script builds an inventory of every file: its extension, its size, and basic risk flags such as empty files, system junk or executables. It can also read deep metadata with ExifTool, like the author, the dates, and the real MIME type. That is how we catch a file whose extension says one thing but whose content says another. One design note: ExifTool is slow, so above two thousand files the script skips that step, but it always completes the inventory.

Core Script Logic

# Inspect_Extensions_Script.R
# 1. Scans target directory
all_files <- list.files(
  path = target_dir,
  recursive = TRUE,
  full.names = TRUE,
  all.files = TRUE
)

# 2. Generates file inventory
inventory <- tibble(FullPath = all_files) %>%
  mutate(
    FileName = basename(FullPath),
    Extension = tolower(file_ext(FileName)),
    Size_Bytes = file.size(FullPath)
  )

# 3. Applies Risk Flags
junk_patterns <- c("\\.ds_store", "thumbs\\.db")
inventory <- inventory %>%
  mutate(Risk_Flag = case_when(
    Size_Bytes == 0 ~ "Zero-Byte File",
    str_detect(tolower(FileName), junk_patterns) ~ "Junk",
    TRUE ~ "Clean"
  ))

Module 2: Tabular Quality Control

Automated structure and content checks for tabular files.

  • Why: Tabular files hide parsing errors, gaps and PII leaks.
  • Obtained:
    • Encoding and schema (rows, columns).
    • Completeness percentage.
    • Duplicate rows and email PII checks.
  • Problems Solved:
    • Parsing issues: encoding or structure corruption.
    • Data gaps: missing values, measured.
    • Privacy risks: raw emails and contacts.
  • Tools: tidyverse, readr, skimr.

Module two: tabular quality control. CSV files look simple, but they hide plenty of problems: odd encodings, missing values, duplicated rows, even email addresses in a column nobody remembered. The script reads every CSV and reports its encoding, its rows and columns, the percentage of complete cells, the duplicate rows, and whether it spotted anything that looks like an email address. It also profiles every variable in detail with the skimr package. And each report ships with a codebook that explains its columns, so nobody has to guess what “percent complete” means.

Core Script Logic

# Inspect_csv_Script.R
# 1. Scans CSVs and runs a health check
analyze_csv_health <- function(file_path) {
  df <- read_csv(file_path, show_col_types = FALSE)
  n_rows <- nrow(df)
  n_cols <- ncol(df)
  n_missing <- sum(is.na(df))
  
  # 2. Regex Check for Email PII
  email_pattern <- "[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+"
  char_cols <- select(df, where(is.character))
  pii_found <- any(str_detect(char_cols, email_pattern))
  
  tibble(
    FileName = basename(file_path),
    Rows = n_rows,
    Cols = n_cols,
    Pct_Complete = round(100 * (1 - n_missing/n_cells), 2),
    PII_Risk = pii_found
  )
}

Module 3: Image Quality Control

Technical validation, fixity and metadata for image collections.

  • Why: Images can carry hidden GPS coordinates or corrupt headers.
  • Obtained:
    • Width, height, format, colorspace.
    • MD5 checksum for fixity and duplicates.
    • Embedded Exif metadata.
  • Problems Solved:
    • Privacy risks: GPS leaks (people, protected species).
    • Outliers: wrong colorspace or dimensions.
    • Obsolescence: raw formats to convert to TIFF.
  • Tools: magick, exiftoolr, digest.

Module three: images. Images are deceptively complex. They can carry hidden GPS coordinates in their metadata, which matters a great deal when the photos involve people or protected species. The script checks that each file opens, records width, height, format and colorspace, and computes an MD5 checksum, which serves two purposes: fixity, and detecting duplicates. It also reads the embedded Exif metadata, and flags outliers, such as an image whose dimensions differ from the rest of the collection.

Module 4: HDF5 Structure and Metadata

Hierarchy, object mapping and attributes of HDF5 files.

  • Why: HDF5 is a binary “black box” of nested groups and datasets.
  • Obtained:
    • Map of groups, datasets and links.
    • Data types and dimensions.
    • Compression filters and user attributes.
  • Problems Solved:
    • Proprietary compression: filters that block reading.
    • Broken links: external files that are missing.
    • Missing documentation: datasets without attributes.
  • Tools: hdf5r.

Module four: HDF5. This format is wonderful for scientific data, but from the outside it is a black box: groups inside groups, datasets, attributes. The script opens each file and maps the whole hierarchy: groups, datasets and links, their data types and dimensions, the compression filters in use, and the user attributes. Why does that matter? Some compression filters are proprietary and can lock future users out, external links can point to files that were never deposited, and datasets without attributes leave their units a mystery.

Array, CF-convention and coordinate checks for NetCDF files.

  • Why: Without metadata conventions, grids and units cannot be interpreted.

  • Problems Solved:
    • Non-compliance: missing Conventions attribute.

Module five: NetCDF, the workhorse of climate and earth-science data. Here the question is usability. Module eight moves from file formats to table structure, and to the idea of tidy data. A table can open without any error and still be hard to reuse: two tables stacked in one sheet, years used as column names, headers with spaces and symbols. This script screens CSV and Excel files for those red flags. It also recommends CSV over Excel, one file per sheet, because CSV is open and machine-readable. One important caveat: these are red flags, not a verdict. A table with no flags is not proven tidy, and a person still needs to read every flag.

Core Script Logic

# Inspect_TidyData_Script.R
# 1. Duplicate headers and embedded blank rows
dup_headers <- headers[duplicated(headers) & headers != ""]
blank_rows  <- purrr::map_lgl(raw_rows, ~ all(is.na(.x) | trimws(.x) == ""))

# 2. Header hygiene: usable as a variable name without renaming?
clean_header <- "^[A-Za-z][A-Za-z0-9_.]*$"
needs_fix <- headers[!stringr::str_detect(headers, clean_header)]

# 3. Format recommendation (CSV preferred over Excel)
Format_Recommendation <- "Convert to CSV (one file per sheet)"

Module 9: README vs. Files on Disk

README file list versus files on disk.

  • Why: The README is the main documentation, but wrong or missing file names go unnoticed.
  • Obtained:
    • Each entry matched: exact, case, or name only.
    • Entries with no file on disk.
    • Files the README never lists.
  • Problems Solved:
    • Typos and missing extensions.
    • Undocumented files.
    • Orphaned entries: renamed or removed files.
  • Assumes: Filename: <name> entries (English or French).
  • Tools: tidyverse, stringr.

Module nine: the README. It is the main piece of documentation in most datasets, yet it is rarely checked against the actual files. This script reads the file list in the README and compares it with what is really on disk. It tells us which entries match exactly, which match only if you ignore case or the extension, which entries point to nothing, and which files on disk the README never mentions. A manual read rarely catches a typo in a file name, but a script finds it in seconds.

Designing for Scale

Inspect enough to be useful, and say what you skipped.

Four Design Principles
  1. Read headers, not payloads. FITS, NIfTI, LAS/LAZ.
  2. List, don’t unpack. zip, rar, OME-Zarr tar.
  3. Sample honestly, and say so. Checksums.
  4. Never execute what you inspect. PyTorch models.
Case Study: PPMstar Simulation Release

Dataset: 3-D PPMstar stellar simulations (Pathak et al., 2026). doi.org/10.20383/103.01782

  1. Structure: release.json versus the disk.
  2. Content: sampled raw cubes; min, max, NaN, Inf.
  3. Fixity: small files all hashed, large files sampled.

In development: not part of today’s live demos.

Before we move on, I want to leave you with four ideas that guide how we write these scripts for large datasets. One: read headers, not payloads. For formats like FITS, NIfTI or LiDAR files, the header already tells us a lot, and reading only that keeps things fast. Two: list, don’t unpack. For zip files or OME-Zarr archives, the listing is enough to audit the structure, and nothing is decompressed. Three: sample honestly, and say so. When files are too big to check completely, the script checks a random sample and labels every file as verified or not sampled, so it never claims more than it did. Four: never execute what you inspect. Our script for machine-learning models, for example, refuses to load files in unsafe ways, because a file that cannot be loaded safely is itself the finding.

A concrete case is a recently published simulation release from the PPMstar project: three-dimensional stellar hydrodynamics, simulating oxygen- and carbon-shell convection in a 25 solar-mass star. A single file can reach several gigabytes, and one run can hold thousands of them. We use three scripts as a pipeline. The first checks the structure, comparing the file counts and sizes the release claims against the disk, without opening a single payload. The second reads a small, reproducible random sample of the raw data cubes and reports basic statistics. The third verifies checksums: every small file, plus a sample of the large ones. The DOI is on the slide if you would like to look at the dataset. These scripts are still in development, so there is no live demo today.
